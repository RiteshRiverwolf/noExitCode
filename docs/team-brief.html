SIH 2026/ Problem 26117/ MRPL · Team brief · Revised 10 Sep 2026

The Air-Gapped Workbench

What we are building, how it works, and what we test next. This revision follows Ritesh's review of the first version — section 11 lists what changed and why.

01

The problem, in plain terms

A refinery produces a lot of routine paperwork: approval notes, inspection reports, engineering calculations, board presentations, small internal tools. Much of it is confidential — process diagrams, financials, vendor negotiations, unreleased designs.

So staff can't use ChatGPT or Claude for it. The problem statement says that leaves two bad options: do the work by hand, or quietly paste confidential material into public tools anyway. We don't have MRPL figures on how often the second happens, so we present it as the problem statement's premise, not as something we found.

Open-weight models are now good enough to build a genuinely useful assistant that runs on hardware the organisation owns. That's the project.

One-line version

An offline workbench that reads confidential documents, links every critical number back to the exact place it came from, flags anything uncertain for a person, and hands back a checked draft — running on the organisation's own computer, with nothing leaving the building.

02

What it has to do

Act, not just answer
Break a job into steps, use tools (read files, run code, search the manuals), check its own work, and retry if something fails.
Pick its own model
A coding request and a document summary get handled by different models automatically. The user never chooses.
Produce real files
A Word approval note, working code, a calculation with its steps — not a chat reply someone has to retype.
Important

These three aren't unique. Free, open-source products — AnythingLLM and Onyx — already do versions of all three. So we don't win by having them.

We win on evidence: every number in our output links to the exact cell it came from, uncertain readings go to a person instead of being guessed, and every draft carries a record of the checks it passed.

04

How we're scoping it

The problem statement's description mentions some things its demo paragraph doesn't name.

CapabilityIn descriptionIn demo paragraph
Scanned PDFsYesYes
Handwritten notesYesNot named
Engineering drawings (P&ID)YesNot named
Word / PPT / Excel outputYesWord only

Not being named doesn't mean judges won't ask about them. So rather than calling them optional, our position is:

  • Printed scans first — that's where open models are genuinely strong.
  • Handwriting, in restricted places: handwritten dates, equipment tags and numbers in known boxes on a form, not free-form notes. We'll measure it on realistic samples.
  • Drawings, as a smaller useful feature: find the right drawing revision, locate a tag, show where it is for a person to confirm. Full diagram reconstruction stays a stretch goal and we never describe it as done.
  • Word first. PowerPoint or Excel only if confirmed as required.

On handwriting: the frightening figure we quoted before — about 28.5% character error for the best closed model — comes from a benchmark of historical and badly degraded documents in 29 languages. It isn't a fair picture of a modern refinery form. The honest answer is that we don't know yet, and we'll find out.

The principle

In a refinery, an assistant that confidently computes on a misread digit is worse than one that asks. Uncertain readings go to a person, together with a picture of the exact cell in question.

05

How the system is put together

Seven layers. Read from the bottom up — each depends on the one below.

L0
The sovereignty boundary
Outbound network traffic is blocked and every attempt is logged, with packet capture as an independent check. It has to cover the Windows host as well as the Linux layer, not just one of them.
L1
Models
Small open models on our own GPU, loaded in stages: the reading model first, then released, then the reasoning model. Models are listed in a settings file, and any new model must pass a compatibility test before it's used.
L2
The document library
An organised library, not a pile of text chunks: a catalogue, a summary card for every document, and a record of revisions. Section 08 explains it.
L3
Tools
Reading scans, making Word files, running code in a sandbox, looking things up in the library. Each is a small local service (the MCP standard) that both our agents and AnythingLLM can use.
L4
Our agent teamwe build
Handles inspection reports, coding tasks and adding new documents. Section 06 explains it.
AnythingLLMwe reuse
Free, open-source platform. Handles general chat, chooses the model for it, and searches documents.
L5
The gateway
Sends each request to the right place — the agent team or AnythingLLM — and records every run.
L6
Our own interface
Chat and upload, plus three things no off-the-shelf interface has: a live timeline of the agents at work, an evidence viewer, and the network panel.

Why build on AnythingLLM

It's MIT-licensed and free, runs fully offline, has a switch to turn its usage reporting off, and — we checked in its source code — its programming interface can run its agents, so our own interface can sit on top of it. Before we commit, it gets a one-day test on our machine. If it fails, Onyx is the fallback, and because our tools are built to a common standard, they move with us.

How the agent team works

Eight specialists, each with one job and a fixed way of handing work to the next. Multiple agents, but no free-for-all.

Standards ResearcherFinds the clause that governs each findingLibrary lookup + search

The line to use with judges

The model explains, the code decides. Whether a report needs escalating is decided by a rule that gives the same answer every time — not by a language model's judgement. The result is one of three: escalate, no rule triggered, or needs a person to look.

Two ideas we borrowed from 2026 research

ICM (a method from the University of Edinburgh). Each agent is a folder holding its own instruction file and an output folder. Every handoff between agents is a file anyone can open and read — including a judge. Each agent also sees only the few thousand words of instructions it needs, rather than everything at once, which matters on a small GPU.

Procedural graphs (a Google paper). A map of how the agents connect, with a short note on each link: when to move on, how, and what to watch out for. The agent sees the notes for where it currently is. Our thickness trap becomes one of those warnings: 

# the link from reading the document to building evidence
pitfalls: a routine-sounding summary does not mean no escalation;
          check every reading against its minimum

The interface draws this map with the current step lit up, so what judges see is exactly what's steering the system.

What we say honestly

  • The Rules Engine is code, not AI — and that's a strength, not something to hide.
  • The inspection workflow follows a known procedure with a few real choices: re-read a doubtful cell, search again, redraft, or send to a person.
  • The Supervisor genuinely plans open-ended requests.
  • Both research ideas were tested only on much bigger models than ours. We say so, and we test them on ours.

What the judges see live

  • The trap report caught: every finding looks minor, one thickness reading is below minimum.
  • A genuinely unclear reading sent to a person, with a picture of that cell.
  • Clicking a number in the draft opens the exact cell it came from and the rule that used it.
  • The finished Word draft with its check record.
  • A coding attempt that fails a test we wrote, gets fixed, and passes.
  • A separately labelled network test, then the clean run.
About the network test

We want to prove the monitor works by letting it catch a deliberate outbound call. But the problem statement asks us to show no external calls at any point. Doing both in one run contradicts itself.

So: a clearly labelled test window where the monitor catches a blocked call, then a separate clean run of the real task. Our claim is precise: "with outbound traffic blocked, the monitors saw no successful external connection during this recorded run."

08

Keeping the knowledge base current

Dumping every document into one searchable pile fails in practice. It can't tell which revision is current, it returns fragments of procedures, and it's bad at exact references like OISD-STD-116 Cl. 7.3 or a tag like R-2247.

An organised library

Every document gets a folder, a one-page summary card (what it covers, its revision, a map of its sections), and an entry in a register that records its revision, whether it's current, what it replaced, and who may see it. A catalogue lists everything in one line each.

How agents look things up

  1. Exact clause numbers and tags — looked up in the register by code.
  2. Otherwise, read the catalogue and summary cards to pick the right documents.
  3. Read the relevant sections directly.
  4. Only then, meaning-based search within those documents.

Adding a new document

Receive it → pull out the text and tables → work out what it is and which equipment it covers → draft its summary card → compare it with what we already have → an engineer approves it → publish it.

  • Nothing is used before it's approved.
  • Old revisions are marked out of date, never deleted. Every answer says which revision it used.
  • Only the new document is processed, not the whole library again.
Example

The manual for a new pump controller, tag P-1107, arrives. Its summary card records the model, its alarm codes, its log format and its limits. An engineer approves it. Later someone asks for a script to flag high-pressure alarms in P-1107's log: the Coder reads the card, then only the log-format and alarm sections, writes the script, and tests it on sample lines from the manual.

If the manual is revised, we can list every script and approval note that relied on the old version. Refineries call this Management of Change — worth saying out loud to judges.

09

Decisions we've made, and why

DecisionReasoning
12GB is our floor, not our ceiling Our test machine has an RTX 4070 with 12GB. The problem statement allows a smaller model at the venue. If it works on 12GB, better hardware only helps.
Build on AnythingLLM, with our own interface Don't rebuild what's free and good. But the parts judges need to see — the agent timeline, evidence viewer, network panel — need our own screens.
The model explains, the code decides A safety decision should give the same answer every time and be explainable to an engineer.
Tools as small local services (MCP), not AnythingLLM add-ons AnythingLLM add-ons must be written in JavaScript; our tools are Python. MCP runs locally with no internet and works with both our agents and AnythingLLM.
An organised library, not a pile Exact references, revisions and approval are what a refinery actually needs. Search is a tool inside the library, not the whole thing.
A tightly locked-down sandbox Uploaded documents — a vendor's file, say — can hide instructions aimed at the AI. So code runs in a fresh, locked container: no network, no access to other files, strict time and memory limits.
Prefer MIT and Apache-2.0 licences MRPL is a public sector undertaking, so licensing gets scrutinised.

What we plan to test

Each test changes one thing at a time, so we know what caused a difference.

Area What we compare What decides it
The platform AnythingLLM, in a one-day test on our machine The whole task works offline, end to end
The escalation decision A model deciding alone vs evidence records plus rules Missed escalations
Reading documents PaddleOCR-VL, GLM-OCR, and a cell-by-cell reading method Mistakes on critical numbers, and how many go to a person
Finding clauses Meaning-based search alone vs exact lookup plus search Finds the right clause in the right revision
Models One general model vs adding a coding model Coding tasks passing tests the model didn't write
The air-gap Firewall, per-process monitoring, packet capture Anything trying to connect out that we didn't expect

Our test data, and its limits

Real documents — a public-domain US Chemical Safety Board investigation of a refinery pipe rupture (132 pages) and a public MRPL tender (486 pages). They're good for testing how well pages are read. They can't tell us whether a value landed in the right table cell, or whether an escalation decision was right.

Generated inspection reports — 12 of them, where we know the right answer for every field. Useful for finding bugs, but too few to prove the system works: with only six escalation cases, getting all six right still can't rule out, with 95% confidence, a miss rate as high as 39%. We need more varied layouts, real scans checked by a person, and pairs of reports that differ by a single digit.
